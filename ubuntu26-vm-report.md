## 3. Введение и контекст

### 3.1. Цели и задачи работы

Целью данного этапа являлось исследование влияния аппаратных ресурсов виртуальной машины на производительность PostgreSQL под нагрузкой HammerDB TPROC-C.

Ключевые задачи:

- зафиксировать матрицу конфигураций C0–C4 с изменением одного фактора за раз;
- провести по одному контрольному прогону для каждой конфигурации;
- сравнить результаты и сформулировать предварительные выводы;
- оставить явный placeholder под повторные замеры C0, которые будут выполнены позже.

### 3.2. Краткий обзор выбранных технологий

| Компонент | Значение |
|---|---|
| Гипервизор | Oracle VirtualBox, ARM64/aarch64 VM |
| Гостевая ОС | Ubuntu Server 26.10 `stonking`, arm64 |
| СУБД | PostgreSQL 16.16 из PGDG (`16.16-1.pgdg26.04+1`) |
| Нагрузочный инструмент | HammerDB 6.1.1, TPROC-C |
| Тест | TPC-C-like, `pg_driver = timed` |
| Хост | macOS 24.6.0 Darwin Kernel Version 24.6.0, 8 vCPU / 16 GB RAM |
| Диск VM | 20 GB, достаточно для `WAREHOUSES=10` |

PostgreSQL и HammerDB запускаются **внутри одной и той же VM**. Это упрощает стенд, но означает, что результат отражает суммарную производительность СУБД и генератора нагрузки.

### 3.3. Методология

Все замеры выполнялись с одинаковыми параметрами HammerDB:

```bash
WAREHOUSES=10 NUM_VU=4 VUSERS=8 RAMPUP=2 DURATION=10
```

Дополнительно в логах зафиксировано:

```text
pg_count_ware   = 10
pg_num_vu       = 4
pg_driver       = timed
pg_rampup       = 2
pg_duration     = 10
pg_allwarehouse = true
```

Перед каждым прогоном схема TPROC-C пересоздавалась (`BUILD_SCHEMA=1`): выполнялись `DROP DATABASE ... WITH (FORCE)` и `DROP ROLE`, затем `buildschema`.

### 3.4. Гипотеза

**H0:** при фиксированном образе Ubuntu 26 arm64, версии PostgreSQL 16.16 и неизменной конфигурации БД изменение vCPU/RAM не влияет на TPM/NOPM.

**H1:** уменьшение vCPU или RAM снижает TPM/NOPM, увеличение — повышает. Матрица C0–C4 построена так, чтобы менять только один фактор за раз: пары `C0 → C1` и `C0 → C2` проверяют CPU, пары `C0 → C3` и `C0 → C4` проверяют RAM.

**Почему здесь образы не менялись.** Этот этап проверяет влияние аппаратных ресурсов, поэтому образ ОС, версия PostgreSQL и настройки СУБД зафиксированы. Сравнение базовых образов выполнено отдельно на Docker-этапе и описано в [docker-containerization.md](docker-containerization.md).

### 3.5. Источник данных

Источник результатов — `results/vm-bench-results.csv`. Конфигурация определяется по колонке `config` и по имени лога. Поле `label` в текущем CSV однотипное (`ubuntu26-arm64-C0`) и в анализе не участвует.

Файлы `vm-results.csv` и `vm-aggregate.csv` относятся к Docker-этапу и в этом отчёте не используются.

## 4. Конфигурации виртуальных машин (C0–C4)

### 4.1. Матрица конфигураций

Матрица построена по принципу **изменения одного фактора**: относительно базовой C0 меняется либо только CPU, либо только RAM.

| ID | vCPU | RAM | Что проверяем | Прогонов сейчас | Повторные замеры |
|---|---:|---:|---|---:|---|
| C0 | 2 | 4096 MB | Базовая линия | 1 | **PLACEHOLDER: 3 повтора запланированы** |
| C1 | 1 | 4096 MB | Меньше CPU | 1 | — |
| C2 | 4 | 4096 MB | Больше CPU | 1 | — |
| C3 | 2 | 2048 MB | Меньше RAM | 1 | — |
| C4 | 2 | 8192 MB | Больше RAM | 1 | — |

Смысл сравнений:

- `C0 → C1` изолирует влияние **уменьшения CPU**;
- `C0 → C2` изолирует влияние **увеличения CPU**;
- `C0 → C3` изолирует влияние **уменьшения RAM**;
- `C0 → C4` изолирует влияние **увеличения RAM**.

### 4.2. Что сохранялось постоянным

Между конфигурациями не меняются:

- версия PostgreSQL и HammerDB;
- параметры HammerDB (`WAREHOUSES`, `VUSERS`, `RAMPUP`, `DURATION`);
- `postgresql.conf` — настройки СУБД не тюнингуются;
- размер диска и тип сети;
- порядок сборки схемы и запуска теста.

На хосте меняются только `VBoxManage modifyvm --cpus` и `--memory`.

## 5. Предварительные результаты: по 1 прогону на конфигурацию

### 5.1. Результаты C0–C4

| Конфигурация | vCPU / RAM | Лог | TPM | NOPM | Δ TPM к C0 | Δ NOPM к C0 |
|---|---|---|---:|---:|---:|---:|
| C0 | 2 / 4 GB | `ubuntu26-arm64-C0_20261125_010649.log` | 109 846 | 47 789 | — | — |
| C1 | 1 / 4 GB | `ubuntu26-arm64-C1_20261125_013558.log` | 101 055 | 43 932 | −8,0% | −8,1% |
| C2 | 4 / 4 GB | `ubuntu26-arm64-C2_20261125_015438.log` | 106 721 | 46 400 | −2,8% | −2,9% |
| C3 | 2 / 2 GB | `ubuntu26-arm64-C3_20261125_023223.log` | 71 580 | 31 129 | −34,8% | −34,9% |
| C4 | 2 / 8 GB | `ubuntu26-arm64-C4_20261125_091101.log` | 152 826 | 66 386 | +39,1% | +38,9% |

Все пять тестов завершились `FINISHED SUCCESS`, сборка схемы — `SCHEMA BUILD COMPLETE`. Версия БД во всех логах: `16.16 (Ubuntu 16.16-1.pgdg26.04+1)`.

Отношение NOPM/TPM во всех прогонах находится в диапазоне **43,4–43,5%**, то есть профиль нагрузки оставался одинаковым.

### 5.2. Почему это пока только предварительные результаты

По одной записи на конфигурацию нельзя рассчитать стандартное отклонение и доверительный интервал. Разница в 2–8% между C0, C1 и C2 может быть как реальным эффектом, так и обычным шумом прогона. Поэтому все выводы ниже помечены как предварительные.

После заполнения placeholder для C0 будет возможно:

- оценить разброс базовой конфигурации;
- понять, превышают ли наблюдаемые отклонения C1/C2 этот разброс;
- сделать окончательные выводы про CPU и RAM.

## 7. Сравнение конфигураций и выводы

### 7.1. Статус сравнений

| Сравнение | Изменение TPM | Предварительный вывод |
|---|---:|---|
| C0 → C1, 2→1 vCPU | −8,0% | 1 vCPU немного снижает результат, но эффект сопоставим с шумом одного прогона |
| C0 → C2, 2→4 vCPU | −2,8% | Дополнительные vCPU не дали прироста; CPU не похоже на узкое место |
| C0 → C3, 4→2 GB | −34,8% | Нехватка RAM явно ограничивает производительность, возможен swap |
| C0 → C4, 4→8 GB | +39,1% | Увеличение RAM дало наибольший прирост в матрице |
| C0 Ubuntu vs C0 RHEL | — | Нет данных по RHEL |

### 7.2. Предварительные выводы

1. **Главный фактор в этой матрице — память.** C4 (8 GB) дал +39% TPM/NOPM относительно C0, а C3 (2 GB) — падение почти на 35%. Это указывает, что при `WAREHOUSES=10` и 8 VU базовая конфигурация 4 GB близка к нижней границе.
2. **CPU не выглядит ограничением.** Переход с 2 на 4 vCPU (C2) не дал прироста, а переход на 1 vCPU (C1) дал лишь −8%. Для текущей нагрузки генератор и СУБД в одной VM, но 2 vCPU достаточно.
3. **C3 требует отдельной проверки.** При 2 GB RAM нужно дополнительно снять `vmstat 1 10`; столбцы `si`/`so` покажут, было ли падение вызвано swap.
4. **Профиль нагрузки стабилен.** Отношение NOPM/TPM практически одинаково во всех конфигурациях, значит, различия не вызваны изменением типа нагрузки.
5. **Выводы про ОС пока отсутствуют.** В `results/` нет RHEL-прогонов.
6. **Замечание про только начальную конфигурацию учтено.** Матрица C0–C4 и гипотеза из раздела 3.4 дают основу для выводов по разным конфигурациям; окончательными они станут после повторов C0.

### 7.3. Ограничения

- по каждой конфигурации есть только один прогон;
- повторные замеры C0 ещё не выполнены — см. placeholder в разделе 6;
- поле `label` в CSV не переименовано, поэтому используется `config`;
- без данных `vmstat` для C3 нельзя окончательно подтвердить swap как причину падения.

## 8. Рекомендации

1. В первую очередь заполнить placeholder C0: три повтора с теми же параметрами.
2. После этого повторить C3 и C4 — конфигурации с наиболее выраженным эффектом.
3. Во время C3 обязательно фиксировать:
   ```bash
   vmstat 1 10
   df -h /
   psql -U postgres -d postgres -c "SELECT pg_size_pretty(pg_database_size('tpcc'));"
   ```
4. Не запускать одновременно две VM на хосте 8 vCPU / 16 GB.
5. Не менять `postgresql.conf` между прогонами.
6. Сравнивать средние значения, а не отдельные прогоны.

```bash

VBoxManage startvm ubuntu26-arm64 --type headless
```
